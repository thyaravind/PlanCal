## High-level findings

**Overall assessment: NOT READY FOR PRODUCTION.**

The project has a solid prototype foundation: Swift 6 strict concurrency is enabled, macOS and iOS release builds pass, all authored unit tests pass, the embedded editor checks pass, the editor bundle is reproducible, and the npm dependency audit is clean.

However, the current app has two immediate release blockers and multiple data-reliability risks:

1. The complete event and Apple Calendar UI is unreachable from shipped navigation.
2. The app uses `UserDefaults` without a bundled privacy manifest, which is incompatible with current App Store required-reason API rules.
3. CloudKit automatic sync is missing the Remote notifications background capability. A signed simulator smoke run logged this as a CloudKit client bug.
4. The app reports `.cloudKit` as soon as the local container opens, even when asynchronous CloudKit setup later fails.
5. Local fallback and CloudKit use different store files with no import or reconciliation path.
6. Most user-data saves suppress errors and often dismiss the editor or claim success anyway.
7. Calendar and SwiftData changes are not transactional, allowing duplicate or orphaned events on partial failure.
8. Recurring calendar events are edited and removed using `.thisEvent`, leaving future occurrences behind.
9. Date-only planning semantics are persisted as absolute `Date` instants and interpreted with the current timezone, so iCloud-synced periods can shift between devices.

## Detailed findings

### Critical

#### F-01 — The complete Calendar feature is unreachable

`README.md:11-12` advertises event creation and Apple Calendar integration. `EventsView` includes event creation, editing, deletion, permission requests, and Apple Calendar display at `Plancal/Views/EventsView.swift:22-95`.

The root navigation only defines Today, Plan, Notes, and Settings:

- `Plancal/Views/RootView.swift:4-8`
- `Plancal/Views/RootView.swift:97-103`
- `Plancal/Views/RootView.swift:123-129`

An iPhone simulator smoke render confirmed four tabs and no Calendar entry.

Impact:

- Users cannot create or edit events through the shipped app.
- The primary route to calendar permission and external event display is absent.
- EventKit implementation and its tests cannot be exercised through normal product flows.

Required fix:

- Add Calendar as a first-class `AppSection` in compact and split navigation.
- Add UI tests asserting all documented top-level surfaces are reachable.
- Treat all EventKit findings below as blockers immediately after navigation is restored.

#### F-02 — Missing privacy manifest blocks App Store readiness

The app directly uses `UserDefaults` in `Plancal/Services/AppleCalendarService.swift:27-44` and uses `@AppStorage` throughout root, planner, today, and settings views.

No `PrivacyInfo.xcprivacy` exists in source or in the built app bundle.

Apple lists UserDefaults as a required-reason API category and requires app code to report covered API use in a bundled privacy manifest. Current submissions that omit required reasons are not accepted.

Impact:

- App Store submission can be rejected before functional review.
- The repository cannot produce a compliant privacy report.

Required fix:

- Add a target-owned `PrivacyInfo.xcprivacy`.
- Declare the approved UserDefaults reason that accurately describes app-preference storage.
- Generate and review Xcode's privacy report for the app and Phosphor package before release.

### High

#### F-03 — CloudKit automatic sync is missing its required background capability

The project declares CloudKit in `Plancal/Plancal.entitlements:5-14`, but `Plancal/Info.plist:29-48` has no `UIBackgroundModes` / `remote-notification` entry.

Apple's SwiftData documentation states that automatic iCloud sync requires both iCloud and Background Modes with Remote notifications enabled.

The signed simulator smoke run logged:

> BUG IN CLIENT OF CLOUDKIT: CloudKit push notifications require the 'remote-notification' background mode in your info plist.

Impact:

- Remote changes may not reach an idle app promptly.
- Cross-device behavior can appear stale or inconsistent.
- The runtime explicitly identifies the capability set as invalid for CloudKit push delivery.

Required fix:

- Add Background Modes → Remote notifications through target capabilities.
- Verify resulting Info.plist/entitlements in an archive.
- Add a two-device or two-simulator sync validation with one app backgrounded.

#### F-04 — CloudKit status and fallback do not reflect asynchronous setup failure

`PersistenceController` sets `.cloudKit` immediately after `ModelContainer` construction at `Plancal/Services/PersistenceController.swift:49-59`.

CloudKit account and mirroring initialization continues asynchronously. In the signed simulator smoke run, the app remained open while Core Data logged:

- no iCloud account;
- failed CloudKit integration setup;
- failed recovery from that setup error.

The UI still reports `syncMode.title == "iCloud Sync"` because `syncMode` is immutable and only represents local container creation.

On iOS, `hasCloudKitEntitlement` returns `true` for every non-test/non-preview process at `Plancal/Services/PersistenceController.swift:87-95`; it does not inspect the actual runtime entitlement.

An unsigned simulator launch crashed with `SIGTRAP` on the Core Data CloudKit queue because the CloudKit entitlement was missing. Tests mask this path by forcing entitlement detection to `false` under XCTest.

Impact:

- Settings can claim active iCloud sync while no account or working mirroring is present.
- Misprovisioned iOS builds can crash instead of entering the promised fallback.
- Current tests do not execute the production initialization branch.

Required fix:

- Separate local-store availability from CloudKit account/sync state.
- Observe and surface persistent-store/CloudKit events and account status.
- Inspect actual iOS entitlements or use an explicit build/runtime policy for unsupported environments.
- Add a non-XCTest launch smoke test for signed, unsigned/misprovisioned, signed-out, offline, and account-restored states.

#### F-05 — Local fallback creates a data fork with no migration path

Cloud and fallback configurations use different names:

- `PlancalCloud` at `Plancal/Services/PersistenceController.swift:51-56`
- `PlancalLocal` at `Plancal/Services/PersistenceController.swift:67-70`

A SwiftData configuration probe confirmed these resolve to different store files, `PlancalCloud.store` and `PlancalLocal.store`.

No import, merge, handoff, or conflict-resolution path exists when the app later changes from local fallback to CloudKit.

Impact:

- Data created during fallback can appear to disappear when CloudKit becomes available.
- Local and cloud histories can diverge with no recovery UI.
- Users cannot export or reconcile the fallback store.

Required fix:

- Define a durable store-state machine and transition policy.
- Detect data in both stores.
- Implement an explicit, idempotent local-to-cloud import with conflict rules and progress/error reporting.
- Back up the source store before migration and test interruption/retry.

#### F-06 — Persistence errors are routinely suppressed and success is falsely implied

Examples:

- Rollover: `Plancal/Services/RolloverService.swift:26-28`
- Quick task creation: `Plancal/Views/PlannerView.swift:306-313`
- Task editor: `Plancal/Views/Editors/TaskEditor.swift:87-108`
- Note editor: `Plancal/Views/Editors/NoteEditor.swift:88-110`
- Task completion/edit: `Plancal/Views/Components/PlanningComponents.swift:212-217`, `334-347`
- Period-note autosave: `Plancal/Views/Components/InlinePeriodNote.swift:104-130`
- Event deletion: `Plancal/Views/EventsView.swift:194-200`

`InlinePeriodNote` updates `lastSavedAt` even when `modelContext.save()` fails. Task and note editors dismiss immediately after ignored save errors.

Impact:

- Disk-full, corruption, migration, or CloudKit-backed save errors look like success.
- Users can leave an editor believing data is durable when it is not.
- Support has no error record or recovery context.

Required fix:

- Centralize saves in a persistence API that returns explicit success/failure.
- Keep editors open on failure and present retry/export/recovery actions.
- Roll back or refetch mutated models after failed saves.
- Record privacy-safe structured diagnostics.

#### F-07 — EventKit and SwiftData writes are not atomic or retry-safe

For new events, `EventEditor.save()` commits the external EventKit event before inserting/saving the SwiftData object:

- `Plancal/Views/Editors/EventEditor.swift:132-161`
- `Plancal/Services/AppleCalendarService.swift:178-180`

If EventKit succeeds and SwiftData fails:

- the external event is already committed;
- the new local object remains unsafely staged;
- retrying creates a new `PlannerEvent` with no identifier and can create another external event.

For deletion, EventKit removal errors and local save errors are ignored at `Plancal/Views/EventsView.swift:194-200`.

Existing event models are mutated before the external operation. If EventKit fails, those local mutations are not rolled back and may later autosave.

Impact:

- Duplicate Apple Calendar events on retry.
- Orphaned external events after local failure.
- Orphaned local events after external deletion succeeds and local deletion fails.
- Error alerts do not accurately describe the resulting state.

Required fix:

- Introduce explicit operation states and idempotency keys.
- Persist a pending local event before external creation, then reconcile the EventKit identifier.
- Compensate external creation/removal when the local phase fails.
- Never discard delete errors.
- Add failure-injection tests for each operation boundary.

#### F-08 — Recurring events are edited and deleted with the wrong EventKit span

`AppleCalendarService` always uses `.thisEvent`:

- Save: `Plancal/Services/AppleCalendarService.swift:171-180`
- Remove: `Plancal/Services/AppleCalendarService.swift:184-192`

Apple defines `.thisEvent` as affecting only one occurrence and `.futureEvents` as affecting the event and future occurrences.

Plancal models recurrence as one `PlannerEvent` with a recurrence rule and no occurrence-scope UI.

Impact:

- Editing a recurring Plancal event can update only one occurrence while the local model represents the whole series.
- Deleting or disabling Apple Calendar sync can remove only one occurrence and leave the remaining series orphaned.

Required fix:

- Define recurrence scope in product requirements.
- For a series-level Plancal model, use an appropriate series/future scope.
- If occurrence-level edits are desired, model exceptions explicitly and ask the user which scope to apply.
- Add recurring create/edit/delete tests.

#### F-09 — Date-only planning data shifts across timezones and devices

Date-only concepts are stored as absolute `Date` values:

- Task `scheduledDate` and `originalDate`: `Plancal/Models/PlannerModels.swift:27-55`
- Period note `anchorDate`: `Plancal/Models/PlannerModels.swift:91-115`
- All-day event start/end: `Plancal/Models/PlannerModels.swift:139-169`

Period membership is recalculated using `.autoupdatingCurrent` at `Plancal/Models/PlannerModels.swift:68-74` and throughout `Plancal/Models/PlanningScale.swift`.

A date created at midnight in one timezone was observed as the previous calendar day in another timezone. This is expected for absolute instants but incorrect for date-only planning identity.

Impact:

- A daily task can move to the previous or next day after iCloud sync or travel.
- Week/month/quarter membership can change around boundaries.
- Period notes and all-day events can appear under the wrong period.

Required fix:

- Persist date-only identity explicitly, such as calendar components plus a defined calendar/timezone policy.
- Normalize all-day event semantics separately from timed instants.
- Define how locale, first weekday, non-Gregorian calendars, and timezone changes affect existing data.
- Add cross-timezone, DST, leap-day, week-boundary, and multi-device tests.

### Medium

#### F-10 — Apple Calendar integration is push-only and can move events unexpectedly

External events are fetched as snapshots and filtered by identifier in `Plancal/Views/EventsView.swift:17-20`, but linked `PlannerEvent` data is never reconciled from EventKit.

If a linked event is edited in Apple Calendar, Plancal continues to show its stale local copy and hides the external copy as “synced.”

`AppleCalendarService.save()` always assigns the current global selected calendar at `Plancal/Services/AppleCalendarService.swift:151-155`. `PlannerEvent` does not retain the event's calendar identifier. Changing the default calendar can therefore move an existing linked event when the user later edits an unrelated field.

The view also lacks an `EKEventStoreChanged` observer and only refreshes through a fragile revision key based on the last event sorted by start date at `Plancal/Views/EventsView.swift:13-15`.

Required fix:

- Define one-way versus two-way sync accurately.
- Store and preserve the linked calendar identifier per event.
- Observe EventKit changes and reconcile linked fields/conflicts.
- Track sync state separately from “identifier is non-nil.”

#### F-11 — Time progression and morning summaries are lifecycle-dependent

`TodayView` captures `Date.now` in a stored view property at `Plancal/Views/TodayView.swift:21`. Rollover and notification refresh run only when the task revision changes or the scene becomes active at `Plancal/Views/RootView.swift:63-69`.

An app left active through midnight has no calendar-day-change observer or timer to advance Today and roll tasks.

Morning summaries schedule only 30 nonrepeating requests at `Plancal/Services/NotificationService.swift:87-105`. If the user does not reopen the app, delivery stops after the window expires.

Per-request failures are stored in one `lastError`, and a later success clears an earlier error at `Plancal/Services/NotificationService.swift:99-104`.

Required fix:

- React to calendar-day and timezone changes.
- Recompute Today/rollover deterministically at midnight and foreground activation.
- Define and test the notification renewal strategy.
- Surface partial scheduling failures and actual pending-summary status.

#### F-12 — Queries and editor bridging are unbounded

Examples:

- Today loads all tasks and events: `Plancal/Views/TodayView.swift:9-10`.
- Planner loads all tasks and notes: `Plancal/Views/PlannerView.swift:7-8`.
- Notes search scans every title and full Markdown document on each query update: `Plancal/Views/NotesView.swift:7-19`.
- EventKit fetches every event from all calendars in a 97-day window synchronously on the main actor: `Plancal/Views/EventsView.swift:183-191`.
- Every editor document change sends the entire Markdown document over the WebKit bridge: `WebEditor/src/editor.ts:351-354`.

No maximum note size, record-count target, paging policy, or performance test exists.

Impact:

- Long-lived users can experience slow renders and memory growth.
- Large notes create full-document bridge traffic per edit.
- Busy calendars can block the main actor while fetching and mapping events.

Required fix:

- Add predicates, paging, and bounded time windows.
- Move expensive EventKit work off UI-critical paths where framework rules permit.
- Debounce or send incremental editor changes.
- Establish and test realistic scale budgets.

#### F-13 — No migration, recovery, or production diagnostics strategy

The app constructs an unversioned `Schema` directly at `Plancal/Services/PersistenceController.swift:30-35`.

No `VersionedSchema`, `SchemaMigrationPlan`, persistent upgrade fixture, downgrade policy, backup/export path, or corrupt-store recovery flow exists.

If the fallback store also fails to open, the production app calls `fatalError` at `Plancal/Services/PersistenceController.swift:67-73`.

No `Logger`, OSLog, MetricKit, CloudKit event observer, or privacy-safe incident trail was found.

Required fix:

- Establish schema version 1 before the first production release.
- Add migration fixtures and reopen tests.
- Replace launch `fatalError` with a recoverable safe mode and export/reset choices.
- Add structured, redacted logging and sync-health diagnostics.

#### F-14 — Passing tests do not cover production failure boundaries

Passing coverage:

- macOS XCTest: 14/14
- iOS XCTest: 12/12
- Editor TypeScript check: pass
- Editor Node tests: 2/2
- Editor browser UI check: pass

Missing coverage:

- Recurring series semantics

- Disk-backed restart and failure recovery
- CloudKit signed-in/signed-out/offline/multi-device behavior

Required fix:

#### F-15 — The icon dependency materially inflates clean build and app size

Measured local release products:

- macOS app: approximately 93 MB, with approximately 84 MB in the Phosphor asset bundle.
- Universal iOS Simulator app: approximately 179 MB, with approximately 168 MB in the Phosphor asset bundle.
- A thinned debug simulator build still included a large Phosphor bundle and took several minutes in `actool` during a clean build.

Actual device/App Store compression and thinning may reduce final download size, but the package dominates both build time and installed artifact size while Plancal uses a small icon subset.

Required fix:

- Measure a signed device archive and App Store size report.
- Prefer a package mode or generated subset that includes only used icons.
- Consider native symbols or project-owned vector assets for the limited icon set.

## Spec conflicts / spec gaps (explicit)

### Spec conflicts

No formal spec bundles exist, so there are no inter-bundle conflicts.

There are implementation-to-documentation conflicts:

1. README says events and Apple Calendar integration are included, but the Calendar surface is unreachable.
2. README says CloudKit initialization failure falls back locally, but asynchronous account/mirroring failure keeps `.cloudKit`, and a missing iOS entitlement can crash outside XCTest.

### Spec gaps

The project needs explicit requirements for:

- durability and failure UI;
- CloudKit state, fallback, migration, and conflict resolution;
- date-only timezone/calendar semantics;

## Cross-cutting audits (security/determinism/limits/errors/compat)

### Security, authorization, and validation boundaries

Positive:

- macOS app sandbox and calendar entitlement are declared.
- Calendar usage descriptions are present.
- CloudKit is configured for a private database.
- The Markdown editor loads a committed local resource.
- WKWebView uses a nonpersistent data store.
- Markdown and command payloads are JSON encoded before JavaScript evaluation.
- The editor bundle contains no external script source.
- npm audit reported zero known vulnerabilities across the installed dependency graph.

Risks:

- Missing privacy manifest and required-reason declarations.
- Task titles are included in notification content.
- No explicit privacy report/release gate exists.
- Link destinations accept any URL scheme; the current editor does not directly navigate them, but rendered-note open behavior should be constrained and tested.

### Determinism invariants

Failures:

- Date-only identity depends on the current timezone/calendar.
- Rollover durability depends on an ignored save.
- Calendar recurrence scope does not match the local series model.
- CloudKit/local store selection can expose different data sets.
- Concurrent creation of the same period note has no uniqueness or reconciliation invariant.

### Limits and caps

Positive:

- Morning summary content is capped to three task titles.
- Scheduling uses 30 requests, below the platform's commonly documented pending-request ceiling.
- Calendar fetch is bounded to a fixed date window.

Gaps:

- No data-record limits or paging.
- No note-size limit.
- No bound on Markdown-to-native message size.
- No cap on EventKit events returned within the date range.
- No release artifact size budget.

### Error handling and canonical envelopes

Positive:

- Calendar save errors in `EventEditor` are shown in an alert.
- Notification authorization errors are retained in `lastError`.
- CloudKit synchronous initialization error text is shown in Settings during local fallback.

Failures:

- Most SwiftData save errors are discarded.
- Event deletion errors are discarded.
- Editor load/evaluation failures are not surfaced beyond a static fallback page.
- Notification scheduling can partially fail while ending with `lastError == nil`.
- No common error model, retry policy, or structured logging exists.
- Fatal store-open failure terminates the app.

### Compatibility, versioning, and migrations

Positive:

- Swift 6 strict concurrency is enabled.
- Release builds pass for both supported platform families.
- SwiftPM and npm dependencies are locked.
- The committed editor HTML is byte-identical to a fresh production build.

Gaps:

- No versioned SwiftData schema or migration plan.
- No archive-level privacy/capability validation.
- Development team is hard-coded in project settings.
- No CI matrix or deployment smoke test.
- Asset catalog warning remains in release/static-analysis output.
